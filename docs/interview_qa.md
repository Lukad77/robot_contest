## 一、基础概念题

### Q1.1 ★ ROS 1 的通信机制有哪几种？项目里分别用在哪？

**答**：三种核心机制：

| 机制 | 特点 | 项目中的使用 |
| --- | --- | --- |
| **Topic（话题）** | 异步、多对多、发布/订阅 | 激光雷达 `/scan`、里程计 `/odom`、速度指令 `/cmd_vel`、图像话题、语音播报指令 |
| **Service（服务）** | 同步、一对一、请求/响应 | 地图服务 `map_server` 的静态地图查询、costmap 清除服务 |
| **Action（动作）** | 异步 + 过程反馈 + 可取消 | `move_base` 导航目标（`MoveBaseGoal`）——导航是长耗时任务，需要中途反馈位姿、支持超时取消重发 |

加分点：能说出为什么导航用 Action 而不是 Service——导航耗时不定，Service 会阻塞调用方且无法取消；Action 提供 feedback/result/cancel 三通道，我在项目里正是基于 Action 的状态回调实现了导航超时重试（`timeoutNavi=5000ms`，`max_retry_count=1`）。

### Q1.2 catkin 是什么？它解决了什么问题？

**答**：catkin 是 ROS 1 的官方构建系统，基于 CMake 封装。核心解决三个问题：
1. **多包依赖管理**：通过 `package.xml` 声明依赖，`catkin_make` 按拓扑序统一编译工作空间内所有包；
2. **环境隔离与叠加**：`devel/setup.bash` 注入环境变量，支持多工作空间 overlay（我的项目是三个独立工作空间，各自 `catkin_make` + source）；
3. **消息/服务代码生成**：自动把 `.msg`/`.srv`/`.action` 生成多语言接口。

追问"为什么分三个工作空间而不是一个"见 Q6.1。

### Q1.3 ★ TF 坐标系统是什么？项目中有哪些关键坐标系？

**答**：TF 是 ROS 维护坐标系之间时变变换关系的树状系统。项目的 TF 树主链路：

```
map → odom → base_footprint/base_link → laser / camera / arm_base
```

- `map → odom`：由 **AMCL** 发布，修正里程计的累积漂移（跳变式修正）；
- `odom → base_link`：由 **robot_pose_ekf** 融合轮式里程计与 IMU 后发布（连续平滑）；
- `base_link → laser` 等：静态变换，由自研 `sebot_transform` 节点上电发布。

加分点：解释为什么 `map→odom` 不直接发 `map→base_link`——TF 树中每个 frame 只能有一个父节点；且把"平滑但漂移"（odom）与"准确但跳变"（map 修正）分层，局部规划器用 odom 系保证控制连续性。

### Q1.4 launch 文件和参数服务器的作用？你的项目如何组织配置？

**答**：launch 文件负责一次性拉起多个节点并注入参数到参数服务器。我的项目把**全部业务关键参数集中在 `sebot_factory.launch`** 里（60+ 个参数），包括：导航超时/重试、四组 PID 系数、三级抓取距离（搜索 1.0m / 机械臂抓取 0.7m / 机械爪夹取 0.55m）、多帧检测确认帧数、边缘补扫时长等。好处是比赛现场调参**不需要重新编译**，改 launch 即生效；`simulation` 和 `debug` 两个布尔参数实现仿真/真机、调试/比赛模式的一键切换。

## 二、SLAM 与定位

### Q2.1 ★ Gmapping 和 Hector SLAM 的区别？你为什么两个都集成、最终用哪个？

**答**：

| 维度 | Gmapping | Hector |
| --- | --- | --- |
| 核心算法 | RBPF（Rao-Blackwellized 粒子滤波），每个粒子携带一张地图 | 高斯牛顿迭代的 scan-to-map 匹配，多分辨率栅格 |
| 是否需要里程计 | **需要**（运动模型做粒子传播先验） | **不需要**（纯扫描匹配） |
| 对雷达要求 | 普通 10Hz 雷达即可 | 需要高频率、高精度雷达，快速旋转时易匹配失败 |
| 弱点 | 粒子数大时内存/计算开销大；无回环检测 | 长走廊等几何退化场景漂移严重；无里程计兜底 |

项目两套都做了 launch 集成，**建图实际用 Gmapping**：因为底盘有编码器里程计 + IMU（经 EKF 融合），Gmapping 能充分利用运动先验；而比赛场地存在相似货架结构，纯扫描匹配的 Hector 有错误匹配风险。Hector 作为备份方案，在里程计打滑严重的场地可以切换。

加分点：说出 Gmapping 的两个关键改进——**改进建议分布**（用扫描匹配结果修正里程计先验，粒子更集中）和**选择性重采样**（Neff 低于阈值才重采样，缓解粒子退化）。

### Q2.2 ★ AMCL 的原理？和普通粒子滤波定位的区别？

**答**：AMCL（Adaptive Monte Carlo Localization）是基于粒子滤波的全局定位算法，循环三步：
1. **预测**：按里程计运动模型（含 `odom_alpha1~4` 噪声参数）传播粒子；
2. **更新**：用激光观测模型（似然域模型，`z_hit`/`z_rand` 权重）给每个粒子打分；
3. **重采样**：低方差重采样，淘汰低权重粒子。

"Adaptive"体现在两点：
- **KLD 采样**：根据粒子分布的离散程度动态调节粒子数（收敛后少粒子省算力，不确定时多粒子保鲁棒）；
- **恢复机制**：通过长短期似然均值（`recovery_alpha_slow/fast`）检测定位失效，注入随机粒子做全局重定位（解决绑架问题）。

### Q2.3 ★ AMCL 参数调优你做了什么？

**答**：结合比赛场景的实际调优经验：
1. **初始位姿注入**：机器人上电位置固定，状态机 `FACTORY_STEP_INIT` 阶段主动向 `/initialpose` 发布已知起点，并以 `initial_pose_retry_interval=1000ms` 周期重发直到位姿收敛（`checkGoal` 校验），避免全局撒粒子的漫长收敛；
2. **取件后主动重定位**：机械臂抓取过程中底盘被 PID 微调过、且长时间低速运动导致里程计误差累积，取件完成后延迟 `post_pick_relocalize_delay_ms=300ms` 重新发布取件台已知位姿，把 AMCL 粒子云"拉回"正确位置——这是把**业务先验注入定位系统**的工程化手段；
3. 更新阈值（`update_min_d/a`）调小以适应比赛中频繁的短距离移动，保证到点精度。

### Q2.4 ★ EKF 是什么？robot_pose_ekf 如何融合里程计和 IMU？

**答**：扩展卡尔曼滤波通过一阶泰勒展开（雅可比矩阵）把非线性系统线性化，然后套用 KF 的预测-更新框架。

**融合动机**：轮式里程计的 x/y 平移可信但 yaw 角受打滑影响大；IMU 的角速度短期精确但积分漂移、无平移信息。两者互补。

**robot_pose_ekf 的做法**（松耦合）：维护 6D 位姿状态，将里程计和 IMU 的位姿测量分别作为观测输入，按各自协方差加权更新——协方差小的传感器话语权大。输出 `odom_combined` 并广播 `odom → base_footprint` TF。

加分点：说明松耦合 vs 紧耦合——松耦合融合各传感器已解算的位姿，实现简单、模块化好；紧耦合直接融合原始观测（如 IMU 预积分），精度上限更高但工程复杂。比赛场景松耦合够用。

### Q2.5 粒子滤波和卡尔曼滤波什么区别？什么场景必须用粒子滤波？

**答**：KF/EKF 假设状态分布是**高斯单峰**的，只能表达"我大概在这里"；粒子滤波用一组带权采样点近似**任意分布**，能表达多峰假设——"我可能在 A 也可能在 B"。全局定位（初始位置未知）和绑架恢复本质是多峰问题，必须用粒子滤波（AMCL）；而里程计+IMU 融合是单峰的局部跟踪问题，用 EKF 更高效。项目里两者各司其职：EKF 管连续平滑的 odom，AMCL 管全局一致的 map 定位。

## 三、导航与路径规划

### Q3.1 ★ move_base 的完整工作流程？

**答**：move_base 是导航栈的调度核心，内部是 PLANNING → CONTROLLING → CLEARING 三态状态机：

1. 收到 `MoveBaseGoal`（Action 接口）；
2. **全局规划**：在全局代价地图（静态地图 + 膨胀层）上，用 Dijkstra/A*（navfn/global_planner）规划全局路径；
3. **局部规划**：DWA 在局部代价地图（滚动窗口，实时融合激光数据）上跟踪全局路径并动态避障，以控制频率输出 `/cmd_vel`；
4. **异常恢复**：局部规划连续失败 → 触发恢复行为链（清除 costmap → 原地旋转 rotate_recovery → 再失败则报 aborted）。

代价地图分层（layered costmap）：static layer（先验地图）→ obstacle layer（实时激光标记/清除）→ inflation layer（按机器人半径膨胀 + 指数衰减代价）。

### Q3.2 ★ DWA 算法的原理？关键参数怎么调？

**答**：DWA（动态窗口法）在**速度空间**采样：

1. **动态窗口**：以当前速度为中心，由加速度限制框定下一控制周期可达的 (v, w) 速度集合，再与最大/最小速度、可刹停约束求交集；
2. **轨迹前向模拟**：对每组采样速度，按运动学模型外推 `sim_time` 秒得到候选轨迹；
3. **代价评分**：`cost = path_distance_bias·贴合全局路径 + goal_distance_bias·朝向目标 + occdist_scale·避障`，淘汰碰撞轨迹，选最优执行。

调参经验：
- 到点精度不足 → 调小 `xy_goal_tolerance/yaw_goal_tolerance`，但过小会在目标点附近震荡；
- 绕障碍太贴近 → 增大 `occdist_scale` 或膨胀半径；
- 项目中比赛场地窄通道多，重点调了膨胀半径和速度上限的平衡：膨胀太大规划不出路径，太小则贴货架擦碰。

### Q3.3 全局规划 A* 和 Dijkstra 的区别？

**答**：Dijkstra 是无启发的均匀扩展，保证最优但搜索面积大；A* 增加启发项 `f = g + h`（h 通常为欧氏/曼哈顿距离），朝目标方向优先扩展，速度快，h 可采纳（不高估）时仍保证最优。navfn 默认 Dijkstra，global_planner 可切 A*。比赛地图小（室内几十平米），两者耗时差异毫秒级，稳定性优先没有特意切换。

### Q3.4 ★ 你的 MultiNavi 多点导航是怎么实现的？为什么不直接连续调 move_base？

**答**：业务需求是"按订单依次途经 工作台 → 取件台 → 结算区"（代码中 `StationNavi` 三类站点）。直接串行发目标的问题是**无异常兜底**：单点卡死会阻塞全流程。MultiNavi 封装了：
1. **目标队列调度**：按订单动态生成导航点序列（点位来自 Qt 标注工具持久化的 `location.xml`）；
2. **超时重发**：单目标 `navigation_timeout=5000ms` 未完成即取消重发，`max_retry_count=1` 次后跳过并在业务层处理，保证比赛计时下"宁可跳过一单，不可全场卡死"；
3. **到点校验**：`checkGoal` 用 AMCL 位姿二次确认实际到达（而非只信 move_base 的 SUCCEEDED），因为結算/取件对停靠精度敏感；
4. **导航后置动作衔接**：到达取件台后进入 PID 精细对位阶段（见 Q5.2），move_base 只负责"粗到达"。

### Q3.5 导航实时性你做过什么优化？

**答**：
1. **分层频率**：全局规划低频（收到新目标或偏离时），DWA 局部规划高频跟踪，控制链路不被全局规划阻塞；
2. **局部 costmap 滚动窗口**：限制局部地图尺寸，激光更新计算量恒定；
3. **参数消灭无效等待**：把状态切换等待压缩到 `inter_step_delay_ms=100ms`，导航目标下发后仅 `navigation_settle_ms=150ms` 短等待；语音播报默认不阻塞导航（`audio_navigation_delay_ms=0`），语音与移动并行；
4. **恢复行为裁剪**：比赛计时场景下压缩恢复行为耗时，超时快速跳转由业务状态机接管，避免 move_base 原地反复自愈浪费时间。

## 四、视觉检测与 NPU 部署

### Q4.1 ★ YOLOv3 的网络结构和检测原理？

**答**：
- **Backbone**：Darknet-53（残差结构），输出三种尺度特征图；
- **多尺度预测**：13×13 / 26×26 / 52×52 三个尺度 + FPN 式特征融合，分别负责大/中/小目标——比赛零件目标较小，多尺度对小目标召回很关键；
- **Anchor 机制**：每尺度 3 个先验框，网络回归框偏移量（sigmoid 约束中心点在网格内）；
- **分类**：独立 logistic 而非 softmax，支持多标签；
- **后处理**：置信度过滤 + NMS 去重。

### Q4.2 ★ 你是怎么把 YOLOv3 部署到 NPU 上的？架构什么样？

**答**：部署在百度 EdgeBoard 板卡（FPGA/NPU 加速），采用**异构两段式推理**（`detection.hpp` 中的实现）：

1. **主干网络 → NPU**：Paddle 模型经 PPNC 编译为板卡指令，`PPNCPredictor` 加载 `config_ppnc*.json` 在 NPU 上跑卷积主干——卷积占推理耗时 90% 以上，交给 NPU 收益最大；
2. **后处理 → ONNX Runtime（CPU）**：框解码 + NMS 导出为独立的 `post.onnx`，用 ONNX Runtime 在 CPU 执行，输入 `im_shape`/`scale_factor` 等张量（`io_paddle.json` 声明张量 IO 映射）。

**为什么拆开**：NPU 只擅长规整的卷积/矩阵运算，NMS 这类控制流密集、动态 shape 的算子不被支持或效率极低；拆分后各跑各的最优硬件。这是边缘部署的通用套路（同类比：TensorRT plugin / 芯片不支持算子回退 CPU）。

### Q4.3 ★ 多帧检测确认策略是什么？为什么需要？

**答**：单帧检测在运动模糊、光照变化下会产生偶发误检/漏检，直接触发抓取代价极高（机械臂动作一次数秒，抓错即丢分）。我设计了**双阈值时序滤波**：
- **确认**：连续 `detection_confirm_frames=5` 帧检测到同一目标才判定"真的存在"；
- **重置**：连续 `detection_miss_reset_frames=8` 帧丢失才清空确认计数——容忍中途少量漏检帧，避免确认过程反复清零。

配合空间过滤消灭背景误检：置信度 `score≥0.5`、检测框尺寸上限（`part_detect_max_width=100`/`max_height=140` 像素，排除近处大框误检）、最低 Y 阈值（`part_detect_min_y=100`，排除桌面以上背景区域）。本质是"时序一致性 + 空间先验"双重验证。

### Q4.4 目标不在视野里怎么办？说说你的边缘补扫策略

**答**：取件台比相机视场宽，零件可能在视野边缘外。搜索流程：中间视角停留识别（`scan_center_duration=800ms`）→ 低速左扫（2200ms）→ 低速右扫（2600ms）→ 回扫停留（800ms）。实现上通过 `scan_yaw_offset=0.02` 的小角度偏置 + `scan_lateral_offset=60` 像素的横向诱导量驱动底盘缓转——偏置过大车身会偏离取件位。单零件搜索总超时 `pickup_search_timeout=13.5s`，超时进入下一目标，防止死循环。这套参数是现场反复实测收敛出来的。

### Q4.5 模型量化了解吗？NPU 部署常见的精度问题？

**答**：EdgeBoard 的 PPNC 编译过程包含定点化（INT8/INT16），要点：
1. **量化原理**：浮点权重/激活映射到定点区间，靠校准数据集统计各层动态范围；
2. **精度风险**：激活分布长尾的层量化误差大，常见对策是敏感层保留 FP16 / 逐通道量化；
3. **工程验证**：我的做法是部署后用比赛零件实拍图回归验证，对比板端与服务器端输出的置信度和框位置偏差，再据此调整 `score` 阈值（最终 0.5）——**部署后阈值必须在目标硬件上重标定**，这是很多人踩的坑。

## 五、机械臂与手眼协同

### Q5.1 MoveIt! 的作用和工作流程？

**答**：MoveIt! 是 ROS 的机械臂运动规划框架。工作流：URDF/SRDF 描述臂体结构与规划组 → 逆运动学求解器（KDL/IKFast）解目标位姿的关节角 → OMPL 采样式规划器（如 RRTConnect）在关节空间规划无碰撞轨迹 → 时间参数化后交给控制器执行。项目中 Talon 六轴机械臂的 MoveIt 配置包（SRDF、关节限位、规划器参数）用于仿真验证与轨迹规划，真机侧由自研串口驱动执行关节指令与动作库（伸展/抓取/放置等预定义动作）。

### Q5.2 ★ 手眼协同抓取的完整流程和坐标转换？

**答**：项目采用"**底盘调整为主、机械臂预定义动作为辅**"的协同策略，分四阶段逐级逼近：

1. **粗定位**（move_base）：导航到取件台前 `disSearch=1.0m` 处（激光雷达有 20cm 盲区需补偿）；
2. **视觉搜索**：YOLO 检测 + 多帧确认锁定目标，得到像素坐标；
3. **精细对位**（像素域视觉伺服）：不做完整的相机标定+手眼标定矩阵求解，而是**以图像中心为目标做像素误差闭环**——检测框中心与图像中心的 X/Y 偏差直接作为 PID 输入（`pidClawX/Y` 两组 PID，Kp 在 1e-4 量级因为输入是像素、输出是速度），驱动底盘微调直至目标居中；同时激光测距 + 距离 PID（`pidDisKp=5.0`）推进到抓取距离 `disPick=0.7m`，方向 PID（`pidPoseKp=12.0`）保持车身正对；
4. **抓取执行**：机械臂执行预定义伸展动作（超时保护 `arm_extend_timeout=7s`），底盘最后推进到 `disClaw=0.55m`，机械爪闭合（`claw_grab_wait_ms=3.2s` 等待夹稳）。

**为什么不做完整手眼标定**：比赛零件位置在固定高度的取件台上，Z 向自由度被约束，像素伺服 + 距离控制的 2.5D 方案足够，且省去标定误差传播链，鲁棒性反而更好。这是面试时的关键叙事——**知道标准方案（eye-in-hand 标定 AX=XB），但能解释为什么选了更简的方案**。

### Q5.3 ★ 四组 PID 分别控制什么？怎么调的？

**答**：

| PID | 控制量 | 输入误差 | 参数特点 |
| --- | --- | --- | --- |
| `pidPose`（12.0/5.0/10.0） | 车身朝向 | AMCL/里程计航向误差 | Kp 大，快速回正 |
| `pidDis`（5.0/0.3/0.0） | 前进距离 | 激光测距-目标距离 | Kd=0，距离量平滑无需微分 |
| `pidLocal`（1e-3 量级） | 位置微调 | 位姿偏差 | 低增益防超调 |
| `pidClawX/Y`（1e-4 量级） | 视觉对中 | 检测框中心像素偏差 | 输入是数百像素，增益必须极小 |

调参方法：先 P 后 I 再 D；像素域 PID 的初值按"最大像素误差 × Kp ≈ 期望最大速度"估算量纲，再实测消震荡；积分项只给存在稳态误差的通道（如爪 Y 向重力性偏差），并做积分限幅防 windup。

### Q5.4 抓取成功率是怎么提升的？

**答**：从"检测、对位、执行、恢复"四个环节分别加固：
1. **检测环节**：多帧确认 + 尺寸/位置过滤（见 Q4.3），杜绝对误检目标出手；
2. **对位环节**：像素 PID 收敛判据 + 三级距离逼近（1.0→0.7→0.55m），每级都有独立校验；
3. **执行环节**：所有机械臂动作带超时（伸展 7s / 放置 10s），动作后强制稳定等待（`arm_post_extend_settle_ms=800ms`）消除臂体振动对下一步视觉的影响；放置阶段限速 `place_approach_out_max=0.1m/s` 缓慢靠台，下探偏移 `place_drop_offset_y=-0.22` 保证贴近桌面释放不摔件；
4. **恢复环节**：抓取后主动重定位（Q2.3），保证下一段导航不因定位漂移失败。

## 六、系统架构与业务状态机

### Q6.1 ★ 三层 catkin 工作空间架构的设计思路和优势？

**答**：按**变更频率和职责**分层：

```
sebot_factory    应用层：比赛业务（状态机/取件/结算/视觉/GUI）→ 高频改动
sebot_ros_kits   套件层：驱动/导航/SLAM/语音       → 稳定，调参为主
sebot_ros_stdr   仿真层：STDR 仿真器及配套          → 几乎不动
```

优势：
1. **编译隔离**：业务层日常迭代只需编译 `sebot_factory`（分钟级），不牵连导航栈全量编译；
2. **依赖边界清晰**：应用层通过标准 topic/action 接口消费套件层能力，仿真层可整体替换真机层——这正是 `simulation` 参数能一键切换的架构基础；
3. **团队协作**：调导航参数的人和写业务逻辑的人互不阻塞。

追问"为什么不用 overlay 链式叠加"：三个空间接口只经 ROS 通信（运行时解耦），没有编译期库依赖，独立空间比 overlay 更简单可控。

### Q6.2 ★ 业务状态机是怎么设计的？

**答**：主状态机 `FactoryStep` 五个状态（`factory.cpp`）：

```
START（上电语音自检）→ INIT（重定位：循环发布初始位姿直到 AMCL 收敛）
→ DELIVERY（送件主循环：按 StationNavi 在 工作台/取件台/结算区 间流转）
→ SUMMARY（智能结算）→ END
```

DELIVERY 内部嵌套站点子状态（`STATION_TABLE / STATION_SERVING / STATION_COUNTER`），每个工作台维护 `Table` 对象（导航点 + 订单列表 + 是否已确认需求标志），实现"多桌多单"的调度。设计要点：
1. **单线程轮询 + 非阻塞状态迁移**：每个状态只做条件判断和一次性动作触发，长耗时操作（导航/机械臂）通过回调/标志位异步推进，主循环不阻塞；
2. **状态入口幂等**：`ordered` 等标志防止重复触发同一动作；
3. **数据驱动**：站点坐标来自 `location.xml`（Qt 标注工具产出），换场地不改代码。

### Q6.3 ★ 异常处理机制有哪些？

**答**：按故障域分层兜底：
1. **节点级**：驱动类节点 launch 里 `respawn=true`，崩溃自动重启；业务主节点启动延时 `delayStart=10s` 等待依赖节点就绪，另有 `navigation_server_timeout=5s` 的 move_base 服务等待校验；
2. **导航级**：超时取消重发（5s × 1 次重试），仍失败则业务层跳过该目标——比赛计时下的止损策略；
3. **感知级**：搜索超时 13.5s 放弃当前零件；多帧确认防误检误动作；
4. **执行级**：机械臂每个动作独立超时，杜绝串口丢包导致的永久等待；
5. **定位级**：初始位姿重发直至收敛校验通过、取件后主动重定位。

总结一句话：**每一个"等待外部结果"的环节都有超时和降级路径，状态机永远不会卡死**。

### Q6.4 仿真和真机切换是怎么做到一键化的？

**答**：`simulation` 布尔参数贯穿业务代码：仿真模式下跳过依赖实体硬件的分支（如 `FACTORY_STEP_INIT` 里 `!simulation` 才等待真机重定位；机械臂/相机链路旁路），底盘与激光话题由 STDR 仿真器以相同话题名提供——**接口不变、实现替换**。开发流程是：STDR 仿真里回归验证状态机与导航逻辑 → 真机只需调传感器和执行器相关参数，把现场调试时间压到最短。

## 七、项目实战与挑战性问题

### Q7.1 ★★ 项目遇到的最大技术难点是什么？怎么解决的？

**答**（推荐讲"视觉引导抓取的可靠性"这条主线，冲突最完整）：

**难点**：比赛计时压力下，"检测到零件"到"稳定抓起零件"之间存在一条长误差链——单帧误检、底盘对位超调、机械臂动作期间车身晃动、抓取后定位漂移，任何一环失败都是整单丢分，且早期实测抓取成功率不稳定。

**解决路径**（体现工程方法论）：
1. **先归因再动手**：把失败样本按环节分类统计，发现三大来源——误检出手、对位不到位就出爪、抓取后导航偏航；
2. **检测侧**：引入 5 帧连续确认 + 8 帧丢失重置的时序滤波，叠加框尺寸/位置先验过滤，误检触发率降到几乎为零；
3. **控制侧**：把一次性对位改为 1.0m→0.7m→0.55m 三级逼近，每级独立收敛判据；像素域 PID 重新按量纲估初值再实测消震荡；
4. **时序侧**：机械臂每个动作后加 800ms 稳定等待，消除臂体振动污染下一步视觉；
5. **定位侧**：发现抓取后导航失败的根因是"低速微调期间里程计误差累积拖垮 AMCL"，加入取件后主动重发已知位姿。

**结果**：全链路在比赛环境下稳定跑通。这个过程的核心收获是：**单点算法都不难，难的是长链路系统里定位"哪一环在拖后腿"的能力**。

### Q7.2 ★ 仿真环境与真实环境的差异（sim-to-real gap）你遇到了哪些？怎么处理？

**答**：STDR 是理想化 2D 仿真，真机差异集中在四类：
1. **传感器差异**：仿真激光无噪声、无盲区；真机 RPLidar 有 20cm 近距盲区——所有抓取距离参数（`disSearch/disPick/disClaw`）都显式做了盲区补偿；
2. **动力学差异**：仿真底盘速度指令即刻生效；真机有惯性、打滑，PID 参数必须真机重调，仿真只验证逻辑正确性、不复用控制参数；
3. **感知链路缺失**：STDR 没有相机与机械臂，视觉/抓取链路在仿真中旁路，用单元测试节点（`unit/` 下 pick/order/pay 独立入口）在真机上分模块验证后再合入全流程；
4. **定位差异**：仿真里程计无漂移，真机必须靠 EKF 融合 + 业务重定位兜底。

**方法论**：仿真管"逻辑回归"（状态机流转、多点导航调度），真机管"参数标定"（PID、距离、超时），两者验证目标严格分离，不指望仿真参数直接迁移。

### Q7.3 ★ 多传感器数据融合的具体实现细节？

**答**：项目里有三个层次的"融合"：
1. **位姿滤波融合**（robot_pose_ekf）：轮式里程计提供 x/y 平移观测，IMU 提供姿态角观测，EKF 按协方差加权——配置上把里程计 yaw 的协方差调大（打滑不可信），让姿态主要信 IMU；输出连续平滑的 `odom_combined`；
2. **全局-局部分层融合**（EKF + AMCL）：EKF 结果作为 AMCL 运动模型输入，AMCL 用激光观测修正全局位姿，各自发布 TF 树的不同段（见 Q1.3），本质是"高频局部平滑 + 低频全局纠偏"的经典分层架构；
3. **异构传感器业务融合**（激光 + 视觉）：精细对位阶段，视觉负责横向对中（像素 PID），激光负责纵向测距（距离 PID）——两种传感器各取所长在控制层融合，而不是在感知层做复杂配准。

追问时间同步：ROS message_filters 可做软同步；本项目控制频率不高（10Hz 量级），时间戳偏差影响可忽略，未做硬同步——**能说清楚"为什么没做"和"什么时候必须做"（高速运动、紧耦合融合）同样是加分项**。

### Q7.4 导航避障的实时性和到点精度怎么平衡？

**答**：这是比赛计时下的核心 trade-off：
1. **分场景精度分级**：途经导航用宽松的 goal tolerance（快），取件/结算等作业点用 `checkGoal` 二次校验 + PID 精细对位（准）——move_base 管"快速粗到达"，PID 管"最后半米"；
2. **速度与膨胀半径联调**：速度上限调高必须同步加大膨胀半径预留刹车距离，比赛地图窄通道多，最终取"能过最窄通道的最大膨胀半径"，再反推安全速度上限；
3. **消灭隐性等待**：状态切换 100ms、目标下发 150ms 的等待都压到最低，语音播报与导航并行；
4. **快速失败**：导航 5s 超时 + 1 次重试即跳过，恢复行为不无限自愈——计时赛里"止损"就是优化总成绩。

### Q7.5 如果这个项目重做一次，你会改进什么？

**答**（展现技术视野，建议按顺序讲 2-3 条）：
1. **迁移 ROS 2**：ROS 1 的 master 单点、TCP 通信延迟不可控；ROS 2 的 DDS + lifecycle node + Nav2 行为树（可替代我手写的状态机异常处理）是更现代的方案；
2. **定位升级**：AMCL 换 Cartographer 纯定位或加入 scan-to-map 的 ICP 精配准，取消业务层"手动重定位"的补丁；
3. **检测模型升级**：YOLOv3 换轻量化的 YOLOv8n/RT-DETR，配合更系统的 INT8 量化标定流程提升帧率余量；
4. **手眼标定正规化**：如果零件高度不再固定（3D 抓取），现在的像素伺服方案就不够了，需要引入相机内参标定 + eye-in-hand 外参标定 + 深度估计；
5. **CI 化仿真回归**：把 STDR 全流程回归做成自动化测试，替代人工回归。

### Q7.6 你在这个项目里最有成就感/最能证明你能力的一件事？

**答**（行为面试题，STAR 结构备一条）：
- **S**：比赛前联调，抓取后的送件导航偶发跑偏，复现率约三成，现场排查时间有限；
- **T**：必须在有限调试窗口内定位根因，不能靠"多试几次"碰运气；
- **A**：没有急着调导航参数，而是用 RViz 叠加 AMCL 粒子云和里程计轨迹观察，发现抓取期间长时间低速 PID 微调让里程计误差悄悄累积、粒子云发散后 AMCL 收敛到了错误峰值——根因在定位不在导航。解决方案是利用"抓取时机器人必然在取件台"这一业务先验，抓取完成后主动重发取件台位姿校正粒子云（300ms 延迟等底盘稳定）；
- **R**：跑偏问题清零，且这个"业务先验反哺定位"的思路后来也用在了初始化阶段。它证明我调试系统问题时会**先建立观测手段、再沿数据流归因**，而不是盲目调参。
